# @jeswr/solid-recipe

Generated recipes and weekly meal plans, browser-safe schema.org JSON-LD import,
ingredient scaling and pod persistence. No network access or remote JSON-LD context
resolution takes place during import. No additional third-party dependency is used.

The ontology, SHACL profile and `codegen.config.json` generate `src/generated/`.
`src/model.ts` is a thin facade for validation and ordered text; it delegates all RDF
reads, writes, parsing and serialisation to generated entities and model-runtime.
Run `pnpm run codegen --update-lock` after changing the inputs. The drift test runs
`pnpm run codegen --out <temporary directory>` and compares every generated byte.

The canonical recipe class is `https://schema.org/Recipe`, at `<resource>#it`.
It carries schema.org `name`, `description`, `image`, `url`, literal `author`, text
`recipeYield`, `prepTime`, `cookTime`, `totalTime` (all `xsd:duration`),
`recipeCategory`, `recipeCuisine`, `keywords`, `recipeIngredient` and
`recipeInstructions`, plus Dublin Core Terms `created` and `modified`.
`schema:nutrition` links to one generated `schema:NutritionInformation` node at
`#nutrition`, with optional text `schema:calories`. No aggregate rating is imported.
`schema:review` links to a generated personal `schema:Review` node at `#review`,
whose `schema:reviewRating` links to a generated `schema:Rating` at `#rating`.
Its `schema:ratingValue` is the owner's optional decimal score between 0 and 5.
`recipe:favourite` is a boolean. No aggregateRating is created.

No recipes federation sector exists in this checkout. Narrowings are stated in the
SHACL header: one literal author name, one source/image HTTP(S) IRI, text yield,
one optional nutrition node, and ordered text instead of RDF lists. Only a nonblank
name is required; ingredients and steps can be added later.

RDF literal sets have no intrinsic order and collapse duplicates. The facade writes
each ingredient and step as a six-digit zero-based position, a colon, and the text:
`000000:2 cups flour`. It sorts and removes these prefixes on read. Equal text at two
positions remains two distinct RDF literals. Plain external strings remain readable
in their dataset order, which other RDF producers cannot guarantee. The generated
core does not support ordered RDF lists or repeated composite children. No generator
or runtime code was changed.

`recipe:MealPlan` uses `schema:name` for the Monday ISO date identifying the week,
and `recipe:monday` through `recipe:sunday` for optional HTTP(S) recipe subject IRIs.
These predicates express dated slots of a particular week; schema.org has no direct
day-to-recipe property. One plan resource and one recipe per day is the first-cut
contract. There are no nested copies of recipe data in a plan.

`fromSchemaOrgJsonLd(json)` accepts Recipe objects, type arrays, top-level arrays,
`@graph` and `mainEntity` wrappers, string/object/array image and author values,
HowToStep/HowToSection instructions, and cooking durations. ISO week durations become
day durations, since `xsd:duration` excludes weeks. Invalid optional values are omitted.
Import ignores aggregate ratings and treats text as text, with no HTML execution.
`extractRecipeJsonLd(html)` returns parsed JSON values from inert ld+json script text;
`importRecipe(source)` selects the first valid recipe. Paste input is capped at 5 MB,
graph traversal at 10,000 nodes and instruction section nesting at 30 levels.

`scaleIngredient(line, factor)` scales initial integers, decimals, ASCII and Unicode
fractions, mixed numbers and ranges. It leaves package sizes and preparation text
alone. `formatDuration` formats fixed cooking durations; month/year durations retain
their original spelling because they have no fixed minute equivalent.

`openRecipeStore({fetch, storageUrl, webId})` uses storage-client and pod-type-index
to create `recipes/` and register schema:Recipe in the private Type Index. Index failure
is exposed as `registrationError`, so callers can explain failed discovery without
hiding accessible recipes. `recipeStore(storage, container)` accepts an existing
client, including memory clients for Solid and LWS. It uses returned create URLs,
observed strong ETags, bounded container listings and conditional writes. Conflicts
propagate to the caller. Weekly plans accept only recipe subjects present in the box.
Registration relies on the pod's existing access policy; this package never grants access.

An explicitly configured `protocol: "solid"` uses the SDK's Solid backend for a known
transport without discovery headers (the Suite demo pod). This is caller configuration,
never a guessed fallback after failed live discovery. The default always discovers
the storage protocol through `createPodClient`.
