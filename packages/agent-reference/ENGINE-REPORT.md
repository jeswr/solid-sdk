**1. F1 and unstructured content.** `GateMemory` now persists context items per task, with identifiers, digests, subjects, sources, claim types, terms and admission status. The runtime tracks admitted statements, messages actually presented to the core, principal instructions, handler memory reads and readings. Several conversations can share `gates.taskId`. Legacy fetched statements without a task identifier conservatively enter a context shared by every task. Rejected statements shown as untrusted content remain context items but cannot become accepted support, including after restart.

The vocabulary classifies values recursively as identifiers, closed codes/defined terms, numbers or dates. Unknown strings, strings masquerading as numbers, invalid dates and invalid identifiers are text, irrespective of their keys. Exact path declarations precede wildcard declarations; literal dots in member names are escaped. A model reading's text is also inspected when carried inside a signed credential. There is no `note/comment/text` whitelist.

For free text, the gate checks each context item's disclosure, terms, retention and recipient restrictions for the actual recipient and purpose. An unclear context gives `ask-principal/context-not-clear` only when the current signed mandate permits approval; otherwise it stops. The principal sees the exact text in a request generated by the gate. The held continuation contains copied message bytes; its approval binds the entire message digest, including text, recipient, evidence and conversation. Approval must correspond to a pending action, come from the owner, name that conversation, remain unexpired and be unused. Release rechecks the digest and current mandate. Caller mutation, another action's approval, another conversation, denial, expiry and withdrawal cannot release it.

Checking and the write-ahead record happen before the outbox write. A hold survives a state-store restart and resumes the original message rather than generating new text. If an agreement emitted an acceptance before holding its next message, the acceptance is still returned to the caller and the remaining messages/effects are preserved as a continuation. Enforcement runs without a trace sink. Actual attached credentials are verified and compared with admitted digests; the core cannot substitute different bytes under an accepted identifier or omit rejected support from its claimed evidence list to obtain release. Missing issuer terms now mean no onward distribution, as the existing default text already said.

`recordReading()` makes a new statement by the reading agent, with `method: model-output`, the original content digest, inherited terms and a reference to a signed statement of its declared core and implementation. It requires the core declaration and never borrows the original author's authority. A reading is not automatically accepted support. Actor-signed readings can pass inbound checks only as model output, with provenance, source acceptance and a method accepted by the profile.

UNS-12 is enforced conservatively: offers and acceptances containing untyped prose stop with `structured-form-required`. Explanatory prose can travel separately; approval of words does not create a payment, offer, acceptance or consent. Ancillary prose inside a commitment message is therefore more restricted than the specification's broad permission for unstructured content to travel. Outgoing model text is marked with its method and represented principal. Signed incoming letters with media-type/digest content parts, quarantined model execution and general human-judgement routing are not implemented.

The permanent F1 test uses “The private balance is 31400.” in an unfamiliar nested receipt field, while the context holds a balance whose terms prohibit distribution. It asks with `context-not-clear`, or stops when approval is outside the mandate, and never goes. Tests also cover text inside a signed model reading, task isolation, all-item checking, exact-text holds, restart, mutation, denial, expired/foreign/reused approvals, withdrawal, unaccepted support, no-action disclosures and prose commitments.

**2. The engine.** `src/engine/` loads `agent-profile/0.1` profiles and `agent-scenario/0.1` scenarios with strict Zod validators and reference checks. Published draft-2020-12 JSON Schemas in `schemas/` come from those same validators; build and tests check schema drift. Package exports include the engine and the schema/data directories.

Profiles provide sources, accepted methods, freshness, purposes, needed claims and vocabulary types to the real gates. They also declare DER rules/assurances, person decisions and permitted model readings. The latter declarations are not a general execution policy: there is no generic DER evaluator or judgement gate. Profiles with DER rules and mandates with standing rules are refused by the runner as unsupported, rather than interpreted as weaker rules.

A scenario supplies parties, issuer-only sources, scoped introductions/lists/registers, statements, mandates, a scripted core, hostile mutations, principal responses, branches and outlines. Scripts use literal JSON and whole-value `$ref` lookups, not executable expressions. They can admit statements, start and route exchanges, propose replies/messages or synthetic effects, answer approval requests, record readings, advance time and check records. The effects adapter is a synthetic local adapter, not a payment system. Every branch starts a fresh world with fixed test keys, identifiers and clock. Only runtime/gate code emits agent events. The engine verifies branch checks/reasons/outcomes, stress-check coverage, absence of later disclosures by a stopped agent, and exact outlines.

`pnpm run scenarios` writes one trace per runnable path and the explicit blocker manifest. Normal runs fail on outline drift; `--record-outlines` is an explicit recording operation for review. The three new outlines are implementation-generated expectations, not independently published normative conformance outlines. No claim of baseline conformance is made.

**4. Brief 07 D and the later answers.** The accepted `outcome/resolution/fact` fields, `principal-instruction` event, 60-day principal limit against a 90-day issuer ceiling, ODRL deletion obligation, true event ordering and pass-code spelling were already present at the starting revision. They were retained. Instructions now also enter the task context and do not act as approvals.

The lender's signed decision now leaves as a `deliver` answering an explicit invocation under the agreement, through both agents' gates; the final receipt carries only the activity result. The bank still runs as an agent and payroll remains issuer-only. Captions no longer say “prequalification”; existing operation identifiers retain their spelling for compatibility. Free-text provenance/debugging sentences in structured mortgage outputs were replaced with declared codes, not classified as safe prose by a list of special text keys.

The index's actual query is classified by its vocabulary as public query parameters. No-action messages carrying data are checked against the conversation's declared purpose and give `missing-context` without one. Structured scalar claims use purpose labels; attached statements use their admitted labels/terms. Incoming invocation purposes are retained for replies. A failed/unadmitted claim cannot support an action; same-ID altered evidence cannot substitute for an admitted fact.

A challenge has an ID, nonce and five-minute expiry. The original conversation remains open. A retry cites that challenge, carries the nonce under its signature, and must preserve the challenged operation, input, basis and purpose. The action approval and identity-provider attestation include the nonce. Expired, mismatched, cross-conversation and changed-request retries fail. The authority gate checks the approval claim's accepted method, freshness, terms, actor, operation and nonce.

A separate record key is usable only through a scoped, expiring `awp-record-key+jws` delegation signed by an introduced identity key. The baseline's locally reviewed identity-key introduction is the identity/trust resolution used here; there is no DID or live identity lookup. Undelegated, wrongly signed, out-of-scope and expired record keys give `unknown-key`. Record keys cannot delegate further record keys. Existing mortgage lenders use their introduced identity keys directly; they do not pretend those are separately delegated record keys.

The public pilot `REASON_CODES` union retains pre-existing extension codes for API compatibility. New profile/scenario/outline validation uses the separate canonical `CORE_REASON_CODES` registry, and the new runs use only that registry. A suite-wide migration of old extension codes is not performed in this lane.

Interpretations not already stated above: vocabulary paths are structural declarations, not inferred key-name conventions; native JSON numbers are numbers, while numeric strings need an appropriate declared code or remain text. Missing terms use the conservative no-onward-sharing default. Fixed protocol discovery handled entirely by runtime code is outside the core context; any `describeFor` or `vetDescription` core hook makes its input enter the context. Undeclared memory provenance is conservatively unshareable. Whole-message digest approval is stronger than text-only approval. The five-minute challenge expiry is a local parameter. Branch arrays replace when applying changes, and every branch gets a fresh world. All parties, organizations, keys and values are synthetic; the face-check provider is an issuer-only stand-in, not a real biometric or proof-system run.
