**1. F1 and unstructured content.** `GateMemory` now persists context items per task, with identifiers, digests, subjects, sources, claim types, terms and admission status. The runtime tracks admitted statements, messages actually presented to the core, principal instructions, handler memory reads and readings. Several conversations can share `gates.taskId`. Legacy fetched statements without a task identifier conservatively enter a context shared by every task. Rejected statements shown as untrusted content remain context items but cannot become accepted support, including after restart.

The vocabulary classifies values recursively as identifiers, closed codes/defined terms, numbers or dates. Unknown strings, strings masquerading as numbers, invalid dates and invalid identifiers are text, irrespective of their keys. Exact path declarations precede wildcard declarations; literal dots in member names are escaped. A model reading's text is also inspected when carried inside a signed credential. There is no `note/comment/text` whitelist.

For free text, the gate checks each context item's disclosure, terms, retention and recipient restrictions for the actual recipient and purpose. An unclear context gives `ask-principal/context-not-clear` only when the current signed mandate permits approval; otherwise it stops. The principal sees the exact text in a request generated by the gate. The held continuation contains copied message bytes; its approval binds the entire message digest, including text, recipient, evidence and conversation. Approval must correspond to a pending action, come from the owner, name that conversation, remain unexpired and be unused. Release rechecks the digest and current mandate. Caller mutation, another action's approval, another conversation, denial, expiry and withdrawal cannot release it.

Checking and the write-ahead record happen before the outbox write. A hold survives a state-store restart and resumes the original message rather than generating new text. If an agreement emitted an acceptance before holding its next message, the acceptance is still returned to the caller and the remaining messages/effects are preserved as a continuation. Enforcement runs without a trace sink. Actual attached credentials are verified and compared with admitted digests; the core cannot substitute different bytes under an accepted identifier or omit rejected support from its claimed evidence list to obtain release. Missing issuer terms now mean no onward distribution, as the existing default text already said.

`recordReading()` makes a new statement by the reading agent, with `method: model-output`, the original content digest, inherited terms and a reference to a signed statement of its declared core and implementation. It requires the core declaration and never borrows the original author's authority. A reading is not automatically accepted support. Actor-signed readings can pass inbound checks only as model output, with provenance, source acceptance and a method accepted by the profile.

UNS-12 is enforced conservatively: offers and acceptances containing untyped prose stop with `structured-form-required`. Explanatory prose can travel separately; approval of words does not create a payment, offer, acceptance or consent. Ancillary prose inside a commitment message is therefore more restricted than the specification's broad permission for unstructured content to travel. Outgoing model text is marked with its method and represented principal. Signed incoming letters with media-type/digest content parts, quarantined model execution and general human-judgement routing are not implemented.

The permanent F1 test uses “The private balance is 31400.” in an unfamiliar nested receipt field, while the context holds a balance whose terms prohibit distribution. It asks with `context-not-clear`, or stops when approval is outside the mandate, and never goes. Tests also cover text inside a signed model reading, task isolation, all-item checking, exact-text holds, restart, mutation, denial, expired/foreign/reused approvals, withdrawal, unaccepted support, no-action disclosures and prose commitments.

**Part 0 — anonymous release.** The gate previously allowed unknown prose when the task context was empty, and did not independently forbid an anonymous `propose` or `accept`. Both were real gaps. Anonymous requests now carry only vocabulary-typed public parameters, using installed identifiers rather than identifiers learned from private context. Parameter names must also be declared, including empty containers; object keys cannot hide data behind an array wildcard. Numeric/date query slots require closed installed values, and the conversation must have been generated by the runtime rather than selected by the core (even if that selected identifier was previously known). They cannot carry credentials, labelled personal data, free text, a core-invented conversation identifier or a substituted address. A commitment without a named principal stops with `representation-missing`. Explicit mandate prohibitions and profile recipient blocks still apply. The runtime binds the actual recipient actor and party to independently introduced keys. The actual message recipient is checked even when a logical action's beneficiary differs from the party receiving its message; that distinction matters for the pilot's internal authorization handover.

`test/anonymous.test.ts` exercises real runtime initiation and continuation, the unsigned public-read evidence/write-ahead path, task context, structured personal data, credentials, both commitment kinds, profile blocks, mandate prohibitions, invented conversation identifiers and encoded recipient addresses. A safe public query still goes with recipient, disclosure and evidence checks. Checks stop at a failure; later checks do not convert a refusal into permission. Existing F1, exact-message approval and identifier tests remain in force. This is the vocabulary/context gate's protection, not a claim to eliminate covert signalling through choices among permitted public query values.

**Part 1 — rules and assessments.** `src/derive/rules.ts` defines the nine closed templates, strict parameters, deterministic evaluation, source aliases and cycle validation. `loadProfile`, reference validation and the runner refuse cycles before execution. Rules may refer to another rule ID or output. The runtime supplies its own task memory; the core cannot pass a list marked “accepted”. Inputs must have matching admitted digests, the same subject and accepted named sources. Current freshness/expiry and permitted purposes are checked. Missing, unaccepted, foreign-task, wrong-source, gapped or otherwise unusable inputs produce no statement with `completeness-not-established`. Currency mixtures and zero denominators also produce no output. No general expression or query language was added. Dependency rules are evaluated recursively under the requested assurance; mixed-assurance chains that rely only on previously held intermediate outputs, and automatic selection of a least-disclosing rule/assurance, are not implemented. An unavailable dependency produces no output rather than a weaker assurance.

The derivation record contains the canonical rule digest and bound parameters, original input digests/issuers/claim types/methods/times/periods/currencies/expiries, intermediate derivation records, output digest, assurance, deriver and run time. Inputs are sorted deterministically. Results carry the oldest input time, original basis methods, shortest input expiry and an intersection of inherited terms. Inherited recipient registration requirements, duties and additional output prohibitions are enforced. The receiver verifies the rule digest and actual output; changed output, parameters, inputs, quality, expiry, chain or terms cannot substitute. Recomputed source acceptance is checked on the original issuers, rather than inferred from the deriver. By-source signatures must be from a source accepted for the rule, over its own inputs; a source runtime needs a separately host-installed source signing key pinned to its party. Both assurances preserve the original input quality. `proved`, `joint` and `attested` are explicit scenario blockers.

`AgentRuntime.assess()` requires the named agreement's permitted purpose, evaluates the installed plan, retains only the selected output plus its terms/quality metadata, removes input payloads and accepted support, records a structured `duty-discharged` receipt and prevents input reuse. Payload-free context tombstones retain source, subject, digest and restrictions: deleting a stored payload does not prove the core forgot it. Retained output restrictions also remain in context. No deletion of remote copies, process memory or a cryptographic proof of deletion is claimed. Tests cover actual agreement formation, missing/wrong purpose, retained output, erasure, inability to rederive, signed recomputation mismatch, aliases, delayed recomputation, every template, cycles, completeness, refused sources/methods and expiry. The statement encoding is the package's JSON encoding, not a new general RDF/CONSTRUCT implementation.

**Part 2 — judgement, roles and approvals.** Profiles now have `personDecisions`. A matching action requires the principal or named role despite an autonomous mandate; the gate builds the request with exact parameters and digest. Roles are ordinary source-signed `organization.role` statements, admitted through the inbound checks. Signed mandate rules can require a count of role approvals and separation from the authenticated requester. The runtime verifies each exact-action signature against an independently pinned staff key, persists its proof, counts distinct people and keys, and rechecks role organization, validity, withdrawal and requester identity. Approvals are consumed at release; they cannot authorize another effect with the same action digest.

**Part 3 — payments.** `pay` has a strict structured parameter schema. The payee/account must match an admitted `payee-account` statement and its current use/sharing terms. Invoice content alone asks for `payee-account` with `structured-form-required`; an explicitly rejected source stops, preserving its source reason. Core prose cannot become a payment. A changed instruction or adapter parameter set cannot ride on an authorization of different bytes. The ODRL adapter normalizes only explicit `pay` permissions to its supported compensation action; existing general `use`/`transfer` grants do not become payment grants.

The local case uses GBP; calendar months are UTC and amounts have at most two decimal places (100 minor units per currency unit), with no currency conversion. Calendar-month totals are integer minor units, keyed by rule and currency in durable runtime state. A release reservation is written before the outbox/adapter; replays do not reserve the same release twice. Per-action and cumulative excess ask with `limit-exceeded` only when the mandate permits a principal exception; otherwise they stop. An approved exception is exact-action and single-use. Tests exercise four £500 payments, a fifth held across restart, a new month, an atomic file-store restart, no-discretion refusal and exact single-use approval. The `pay-an-invoice` main path includes the separately keyed bank's inbound checks, payment/effect gate, recorded submission and signed result. Both catalogue branches run. **Part 4 — corroboration.** Claim rules can require a source count and independent controllers. Candidates must independently pass signature, source, terms and ordinary fitness checks. Only matching subject, claim, value and period count; duplicate issuers and controllers do not increase the independent count, and absent/empty control provenance contributes nothing. Disagreement or insufficient support asks with `completeness-not-established` and names the claim. Controller identity comes from the installed trust store, not a claim's own assertion. Corroboration is evaluated over the supplied admission batch; a quarantined cross-message collection/retry service is not implemented.

**Part 5 — scoped pins.** The runtime holds a verified but unaccepted sender's message outside core context, without admitting it or learning its identifiers.
